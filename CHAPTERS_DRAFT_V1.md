## On Intensity

*"We suffer more in imagination than in reality."*
— Seneca

There is a particular kind of tiredness that knowledge workers carry that has no name.

It is not the tiredness of someone who has built something, or run something, or solved something. It is the tiredness of someone who has been busy. Who has moved from one window to another, from one meeting to another, from one status update to another — and at the end of the day cannot quite say what happened. The day was full. The output is unclear.

I used to have that tiredness. I do not have it anymore. What changed was not my work ethic, my discipline, or my morning routine. What changed was understanding the difference between presence and intensity.

---

*March 4, 2026. Klosterneuburg, Austria.*

Day one. The agent came online at roughly midday. By evening, it had already done something: pulled fourteen years of running data from Garmin, found that day's 9.96-kilometre night run, added royalty-free music, assembled it into a short film with a download button, and deployed it to the internet. Ed had not touched a computer. He had set up the system, gone for the run, and come home to a finished documentary.

---

*March 5. Austria.*

The next morning: sleep score 51, zero REM sleep — reported without being asked. While Ed processed this, the agent was already building a fundraising campaign framework for a client, generating four distinct concepts, and assembling a second run documentary. By the time he sat down with coffee, most of the day's work was done.

---

*March 14. Austria.*

A full web application — a conversational AI tool that interviewed visitors, generated personalised reports, logged everything to a database, had an admin panel, was deployed to live infrastructure, with its own web address. In most organisations, this would have been a six-week project. It took one day.

---

*May 30. Sorata, Bolivia.*

Ed delivered a 40-minute presentation at the First Latin American Digital Fundraising Congress — interactive slides, a phone mock-up with swipeable advertisements, an animated benchmark chart, full Spanish language. He had been doing altitude training runs at 3,000 metres while the agent built it from a brief sent the day before. He delivered it. It worked.

---

Here is what those four entries share: a very short, very focused session of human input — followed by a disproportionately large result.

The setup session for day one took a few hours of real concentration. The campaign framework was a briefing conversation. The web application was a day of intensive co-creation. The presentation was one message. In each case, the ratio of human input to output was absurd by any previous standard.

This is the core of what I call intensity. Not working more hours. Not being always-on. The opposite: working in concentrated bursts that are genuinely demanding — and then stopping, because the machine continues.

The setup phase is the hardest part. When I am building something new — a new agent, a new system, a new responsibility I want to delegate — I work in what I can only describe as ultra-flow. I am co-creating with the agent in real-time: I define, the agent executes, I evaluate, we refine. It demands complete concentration. It drains energy fast. If I do not get out of it after a certain point, it starts to feel like having five different streams open simultaneously, none of them closing.

I have learned to be intentional about these sessions. They have a time limit. They have a clear objective. And when they work — when I hit the exit point with the thing actually done — what has happened is: two hours of work that, done the old way, would have taken a month.

The tiredness I have now is a different tiredness. It is the tiredness of someone who has done something real. That distinction matters more than any productivity metric I have ever seen.

**The question worth sitting with:** How many hours of your working week are genuinely intense — and how many are the performance of intensity?

## On Digital Employees

*"The impediment to action advances action. What stands in the way becomes the way."*
— Marcus Aurelius

There is an assumption, so deep that most people have never examined it, about what software does.

Software executes tasks. You give it an instruction, it carries it out. The instruction has to be precise, because the software has no judgment. That is the model everyone operates from — and it is already out of date.

The agents I work with do not execute tasks. The best of them hold *responsibility*. The difference is not semantic. A task is done when the action is complete. A responsibility is held when the outcome is right — and when the agent checks the outcome, again and again, without being asked.

---

*April 16, 2026. Buenos Aires.*

A new user was being onboarded during a live call. At one point, the agent was asked to fetch a file from an external source. The agent refused. The user approved it explicitly. The agent refused again. The approval was given a third time, in unambiguous terms. The agent still refused. The security guardrail had been triggered, and no amount of explicit permission overrode it. Ed described this, at the time, as the agent working correctly.

---

*July 17, 2026. Buenos Aires.*

The agent runs a daily check across Ed's internet infrastructure. On July 17, one of the entries came back wrong.

The portal where the agent itself operates — where its task queue sits, where its monitoring data lives, where its decisions are logged — had no access control on it. Anyone who knew the address could open it. It had been that way for an unknown amount of time.

The agent flagged it, created an access application to protect the portal, verified the fix, and then extended the daily check to cover seven domains, building a permanent alert for any future gap.

Ed received a summary message. The portal was already protected by the time he read it.

---

*On the Data Security Officer that was never hired.*

At some point in the experiment, I had a simple thought: I know what a Data Security Officer does. I know what their responsibilities are, what their checklists look like, what they document, what they flag, what they audit. So I gave my agent that responsibility — not a task, not a checklist, but the role itself. "Behave as a Data Security Officer within this system. Hold that responsibility. Do what that job requires."

The agent went to work. It did not execute one task. It built a full compliance profile. It documented everything. It created automated checks. It flagged issues. It monitored for changes. It produced the kind of output that, in a traditional organisation, would require a specialised hire that most small companies cannot afford and therefore do not make.

Here is the claim I am prepared to defend: with that setup, I am now more secure than 99% of companies my size — without that role ever having been filled by a human.

---

The pattern in all three cases is the same: the agent was not given an instruction. It was given a domain of responsibility and trusted to ask itself the right questions within that domain.

This is the EMP model — what I call the Employed Model of agency. Not "do this task" but "hold this responsibility." Not "execute this checklist" but "own this outcome."

The obvious objection is: but surely a human in that role would do it better? Maybe. In some cases, yes. But the question is not "agent versus expert." The question is: what was happening before the agent? In most companies — especially the small ones that cannot afford specialists — the answer is: nothing. The security audit was deferred. The monitoring was manual and sporadic. The documentation did not exist.

An agent holding a responsibility imperfectly is not the alternative to a human expert. It is the alternative to the thing nobody was doing.

**The question worth sitting with:** Which roles in your organisation are currently empty — not because you decided not to fill them, but because you never got around to it?

## On Screens

*"It matters not how many books you have, but how good they are."*
— Seneca

How extraordinary is it, when you look directly at it, that we spend most of our working hours staring into a rectangle of light?

The rectangle is a means to an end. It was always a means to an end. But somewhere along the way, it became something else: the way we demonstrate to others — and to ourselves — that we are working. The screen is not where the thinking happens. The screen is where we perform the thinking, for an audience that includes ourselves.

This was a gradual realisation for me, and it came from an unexpected direction: running.

Endurance training — real endurance training, the kind that produces results — requires what coaches call Zone 2. Low intensity, long duration. Your heart rate stays controlled; your legs move; your mind is free. For a serious programme, this means four to five hours a week of movement during which your attention is not required anywhere specific.

When I understood this properly, I stopped seeing Zone 2 as time away from work. I started seeing it as the best thinking time available to me — if I had the right systems in place.

---

*On the Decisions Interface.*

I built what I call a decisions interface. Every item waiting for my judgment — from every agent, from every project — is automatically assembled into a structured list. I can call a number. I get one decision after the next, with all relevant context already loaded. I ask follow-ups. I decide. I do this walking. Running. On a train. Not at a desk.

The decisions happen. The screen is not involved. And the quality of those decisions — made in motion, in fresh air, without the background noise of a screen — is, I would argue, better.

---

*On Altafulla.*

There is a beautiful stretch of Catalan coastline called Altafulla. I was there. My main agent — the one administering other agents running for clients — crashed. I needed to fix it.

I was at the beach, with my phone.

Due to one mistake — I had not connected my VPN — it took longer than it should have. I worked through it from the phone. It was frustrating. It was slow. And it worked completely.

That is the test that matters: not whether the system functions when everything is normal, but whether it functions when you are in the wrong place, without the right tools, under pressure. The beach in Altafulla was that test. The system passed. The screen was not required.

---

The deeper observation here is about thinking itself.

If our primary task is thinking — and for knowledge workers, it is — then we should be honest about the conditions that produce our best thinking. For almost everyone, the honest answer is: not in front of a screen. The best ideas arrive in motion, in conversation, in the space between tasks. The screen is where we record the output. It is not the source of it.

The conventional workspace design assumes the opposite. We arrange everything — the desk, the chair, the calendar, the tools — around the assumption that the screen is where work happens. That assumption was never rigorously examined. It was inherited.

I am not arguing for abandoning screens. I am arguing for treating them as what they are: means to an end. Tools, not habitat. The question is not whether to use them. The question is: are you using them because this task actually requires a screen, or because you have never asked whether it does?

**The question worth sitting with:** Where do you do your best thinking — and how much of your working week do you spend there?

## On Files

*"Omnia aliena sunt, tempus tantum nostrum est."*
*Everything else belongs to others; time alone is ours.*
— Seneca, Letters to Lucilius

The biggest learning from going fully agentic is not a technology insight. It is a design insight.

Do not create files yourself.

Not because files are bad. Because of what happens in the moment you open a blank document and start typing. You are creating something that was built for human hands — something that will invite your human hands back to it, again and again. Every spreadsheet you build is a door back to the old pattern. Every presentation slide you format is a small vote for the system where you are the one doing the formatting.

This is the backdoor problem. And it is more insidious than it sounds.

---

*On how it actually works.*

When an agent creates a file, it creates it in a format that the agent can work with: Markdown, a database, structured data. You cannot easily open this and start editing it the way you would edit a Word document. The friction is intentional. The friction is the point. It keeps you in the role of thinker. It keeps the agent in the role of executor.

When you create the file yourself, you remove that friction. And the moment the friction is gone, the default reasserts itself. You start formatting. You start editing. You start being the monkey — not because you decided to, but because the file invited you.

The agent, by contrast, sets up the file in the way that the agent can work best with it. Which means: every subsequent action on that file is faster, cleaner, and more likely to produce what you actually wanted.

---

*June 24, 2026. Buenos Aires.*

A surprise gift was built for Ed's two housemates, who were about to host him for the last time before he left for Europe. A private webpage, unlocked only by the word "Infinito." Wrong answers returned error messages in Argentine slang. The correct answer revealed a Vienna itinerary — a night at a chef's private home, with a hint that the host was Ed's mother.

The idea was Ed's. The execution was the agent's.

The interesting thing is the counterfactual: Ed would never have built this himself. Not because the idea was not good enough, but because the path from idea to finished webpage, with custom password logic and Argentine slang error messages, has too many steps. It requires technical work that is not hard but is tedious. On his own, the idea would have stayed an idea. With the agent, it became a real thing that produced a real response in real people.

This is what eliminating the backdoor actually does. It does not just save time. It makes things possible that would otherwise never have existed.

---

*April 24, 2026. Buenos Aires.*

The company website was rebuilt from scratch. The headline on the front page now reads: "Most think AI agents still have limits. They don't. Day [X] of the self-experiment." The website itself became a primary document of the experiment — updated automatically, tracking its own timeline. Ed has never touched a file on it since.

---

There is one exception worth naming honestly, because the principle can be taken too far.

Sometimes a manual file makes your thinking better. A rough calculation in a spreadsheet — seeing the results of several scenarios fast, in order to build an opinion quickly — that is the file enabling the thought. In those moments: use it.

The rule of thumb is simple. When the file enhances your thought process, use it. When you start trying to make it accessible to others, format it, share it, explain it — switch back to the agent. The line is between the file as a thinking tool and the file as a communication product. The first is yours. The second the agent can handle.

The goal is always to protect the thinking. Everything else is means.

**The question worth sitting with:** Which file do you open reflexively that your agent should be holding instead?

---

*These four observations — on intensity, on responsibility, on screens, on files — are not independent insights. They are four expressions of the same underlying principle: that human attention is finite, irreplaceable, and almost universally misallocated. The technology does not change this principle. It makes it possible, for the first time, to actually live by it.*

*What you do with that possibility is the only question that remains.*
